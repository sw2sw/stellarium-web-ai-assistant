# 时间控制（助手 0.7.0 起；桥接 0.7.0 提供命令预检，0.9.0 起提供逐帧跳时计数，0.10.0 起自身写入当场登记）

从"跳到某个时刻"到"以 1000 倍速度走过一天"，这一层在 0.7.0 之前是不存在的：
引擎一直有倍率，上游前端只做了播放/暂停。

## 1. 引擎里到底有什么

| 位置 | 事实 |
|---|---|
| `src/core.h:146` | `double time_speed; // Time update speed factor: 0=stopped, 1=real time.` |
| `src/core.c:1047` | `PROPERTY(time_speed, TYPE_FLOAT, MEMBER(core_t, time_speed))` —— 挂在属性系统上，JS 里 `stel.core.time_speed = N` 可直接写 |
| `src/navigation.c:51-52` | `tt = core->observer->tt + dt * core->time_speed / 86400` —— 每帧按倍率累加，真·线性倍率 |

**没有任何 clamp**。`PROPERTY` 直接映射到成员，C 层不校验范围，也不校验符号。所以
`0` 停、`1` 实时、`86400` 每秒一天、负数倒放，全都能写进去。这是本项目所有上限的由来：
**上限不是引擎给的，是我们加的**。

## 2. 上游为什么没有倍速

`apps/web-frontend/src/` 里只有两处碰过 `time_speed`：

- `App.vue:133`：初始化 `this.$stel.core.time_speed = 1`
- `components/date-time-picker.vue:155`：`= (time_speed === 0) ? 1 : 0`

`date-time-picker.vue:142` 的 `isTimePaused` 也只看 `=== 0`。也就是说，上游的"时间控制"
是一个播放/暂停按钮，没有档位、没有滑块、没有 URL 参数（`App.vue` 的 `query` 只处理
`date/lat/lng/az/alt/fov/sc`）。桌面版 Stellarium 的时间流速控件，Web 版没有对应实现。

**结论：不需要改引擎就能加倍速。** 属性已经导出，缺的只是命令和界面。

## 3. 命令契约

```json
{"type":"set_time_speed","factor":1000}
{"type":"set_time_speed","factor":1000,"simHours":24}
{"type":"set_time_speed","factor":0}
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `factor` | 是 | 倍率。`0` 停，`1` 实时，`N` = 每 1 秒真实时间走 N 秒模拟时间。负数倒放 |
| `simHours` | 否 | 从当前时刻按该倍率走这么多**模拟小时**后自动停表 |

读回（`readback`）：

```json
{"requested":1000,"factor":1000,"running":true,"direction":"forward",
 "simHours":24,"realSeconds":86,
 "startedUtc":"2026-11-01T12:00:00.000Z","stopAtUtc":"2026-11-02T11:59:59.999Z","autoStop":true}
```

`state.time` 也从 0.6.0 起多两个字段：`speed`（数值倍率）和 `running`（布尔）。
面板据此显示"3600× 实时 · 运行中"，模型据此知道时钟已经在跑、不用重复设。

### 3.1 为什么是 simHours 而不是"真实秒数"

因为**模型算数不可靠**。"1000 倍走一天要多久"要先算 `86400/1000 = 86.4`，
这一步在提示词里出现，模型就会时不时算错（写成 864 秒、写成 24 秒）。
让模型只说"走 24 模拟小时"，换算交给代码：`realSeconds = simHours * 3600 / |factor|`。

### 3.2 上限

| 项 | 上限 | 为什么 |
|---|---|---|
| `\|factor\|` | 86400 | 每秒一天。再快就是跳变而不是流动，星表边界和坐标精度都会出怪象 |
| 非零 `factor` 下限 | 0.0001 | **应用侧的可感知下限，不是浮点下溢的证明**：`1e-4` 已经意味着 2.8 小时真实时间才走 1 模拟秒，课堂上看就是"没动"。把它写成拒绝值，是为了让"设了速度却看不出在动"变成一个明确的 `out_of_range`，而不是让老师盯着静止的星空猜原因 |
| `simHours` | 100000 | 约 11 年模拟时间，够任何课堂演示 |
| 折算真实耗时 | 72 小时 | 更长的自动停表等于永远不停，只会留下一个再也不触发的定时器 |

超限返回 `out_of_range` 并说明具体原因（例如"按这个流速走完 100 模拟小时要 36000000 秒真实时间，超过上限 259200 秒"）。

## 4. 自动停：为什么盯引擎时钟而不是墙上时钟

`armAutoStop()` 每 200 ms 读一次 `observer.utc`，越过 `stopAtUtc` 就把 `time_speed` 置 0。

不用 `setTimeout(realSeconds * 1000)` 的理由是浏览器：

- 后台标签页会把定时器节流到每分钟一次，`setTimeout` 会晚到；
- 标签页挂起时渲染循环停摆，引擎时间根本没走，`setTimeout` 却照常到期，
  结果是"还没走完就停了"；
- 反过来，掉帧时引擎走得慢，`setTimeout` 又变成"时间没走够就停"。

比对 `observer.utc` 对这三种情况都免疫：只要没到目标时刻就不停，到了就停，
哪怕晚了 200 ms 也无所谓（200 ms × 1000 倍 = 3 分钟模拟时间，可接受）。

### 4.1 与 set_time 的交互

`set_time` 会**清掉**待触发的自动停表，并在读回里标 `autoStopCleared: true`。
理由：跳时刻之后，原来那个终点已经不在同一条时间线上了。这也意味着**命令顺序必须是**
`set_time` → `set_time_speed`；反过来写，刚设的停表会被 `set_time` 清掉。
提示词里把这条写成了显式规则。

`set_time_speed` 自身也会先清掉旧停表——两个停表抢同一个时钟没有意义。

## 5. 完整示例

需求原话："时间跳到某一个时刻，用某个天体作为视场中心，然后以 1000 倍的速度走过一天。"

```json
{"commands":[
  {"type":"set_time","utc":"2026-11-01T12:00:00Z"},
  {"type":"select_object","name":"NAME Jupiter"},
  {"type":"set_time_speed","factor":1000,"simHours":24}
],"say":"已跳到 20:00，木星居中，1000 倍速开跑，走完一天自动停"}
```

三条命令，`2026-11-01T12:00:00Z` 是北京时间 20:00。桥接算出的计划是约 86 秒真实时间后自动停，
`realSeconds` 与 `stopAtUtc` 会随结果一起返回，面板照此显示倒计时。

其他常见写法：

| 想要 | 命令 |
|---|---|
| 暂停 | `{"type":"set_time_speed","factor":0}` |
| 实时 | `{"type":"set_time_speed","factor":1}` |
| 倒放看前一天 | `{"type":"set_time_speed","factor":-3600,"simHours":24}` |
| 快进到日出（不自动停） | `{"type":"set_time_speed","factor":3600}` |
| 每秒一天 | `{"type":"set_time_speed","factor":86400}` |

## 6. 界面

边栏从 0.7.0 起分四个分页：**星空 / 视图 / 时间 / 设置**。"时间"页上半是原有的
跳转输入，下半是新的流速控件：

- 播放/暂停按钮（暂停后回到上次的倍率，不会重置成 1×）
- 四个档位：`1×` `60×`（1 分/秒）`3600×`（1 时/秒）`86400×`（1 天/秒），当前档位高亮
- 自定义倍率 + 模拟小时数 + "开跑"（留空小时数就一直跑，填了就自动停）

按钮走的是同一条 `set_time_speed` 命令，所以**老师点"1000×"和老师打字说"1000 倍走一天"
落到完全相同的时间状态**，不存在两套实现。

"设置"页是原来的 AI 表单，从长列表底部提上来单独一页——之前七个小节加一个 AI 表单
挤在一列里，笔记本屏幕上输入框会被顶出视野。

## 8. "星图还是当初那张吗"：时间这一项怎么判（0.12.0）

提案在提问时冻结一份上下文，回答到达时和确认执行前各比一次；批次每执行完一条命令
再比一次，比较的是**这条命令不该动的东西有没有动**。其中最难的一项是观测时间。

### 8.1 为什么不能靠"算了多少"来判断

面板拿不到引擎的积分过程，只能看时钟。用"时钟走了多少 vs 倍率应该走多少"来判断，
有两个绕不过去的毛病：

1. **自身改倍率被当成外部改动。** 执行 `set_time_speed` 时，从快照到读回之间时钟先按
   旧倍率走、后按新倍率走，切换发生在观测不到的时刻。0.10.0 的做法是把允许范围扩成
   两个倍率之间的整条带——0.11.0 的复核指出，这条带本身有问题（见下条）。
2. **容差随倍率放大，大到盖住真的跳时。** 引擎按自己的帧时长积分，一次读回最多落后
   一帧；3600 倍下一帧就是约 60 秒模拟时间。要盖住一帧的滞后，容差就得给到"几十秒 +
   35% × 预计位移"，于是 0→3600 倍、间隔 1 秒时额外容差达到 **1400 模拟秒**，
   落在这段窗口里的并发 `set_time` 会被静默吞掉再被重新锚定。

结论：**时钟读数的算术判不出这件事**，因为噪声和信号在同一个量级上。

### 8.2 现在怎么做：桥接按帧计数

桥接（`loader.js` 0.9.0 起）自己跑一个逐帧监视器（`requestAnimationFrame`）：

- 每一帧读一次 `observer.utc` 与 `core.time_speed`，算出这一帧该走多少
  （`[min(旧倍率, 新倍率), max(旧倍率, 新倍率)] × 实测帧间隔`）；
- 允许量是 `2 秒 + 50 ms × 倍率`——只为盖住"读到的值最多落后一帧"这件事；
- 超出的位移算一次跳时，累加到 `readState().time.jumps`（单调递增）；
- 本桥接自己执行的 `set_time` **在写入的那一瞬间**就计一次跳、并把帧基线重锚到刚写进去
  的值（0.10.0 起，见 8.6）。计数器因此仍然只说明"时钟被移动过"，不区分谁动的：
  发起方按"这条命令允许改时间"豁免自己那条命令，别的写入（宿主时间面板、快捷键、
  别的页面）照计不误；
- 单帧超过 250 ms（切到后台、卡顿）时丢弃这次采样并重锚，避免把引擎的步长钳制
  误判成跳时。

面板只比较两次读到的 `jumps` 是否相同：变了就是外部动过时钟，没变就是没动过。
0.10.0 那套"整条带 + 大容差"只在桥接低于 0.9.0（没有计数器）时作为兜底保留。

### 8.3 检测下限（说清楚边界）

一帧就是检测下限：3600 倍下约 60 秒、7200 倍下约 120 秒以内的一次跳时，可能落进
"落后一帧"的允许量里分不出来。这比 0.10.0 的 1400 秒小一到两个数量级，而且**不再随
命令时长放大**——原来是一条命令执行 2 秒，窗口就是 2 秒；现在只有那一帧。

"暂停后立刻恢复"仍是靠 `speed` 字段判定，不靠时间差。

### 8.4 上下文改为现读

同一轮还改了一处：`captureContext()` 现在优先调用 `bridge.readState()` 现读，
而不是用订阅推送的那份（最旧可能差半秒）。冻结上下文、每条命令执行前、执行后比较
都用现读的值——"这条命令跑的时候有没有人动过"是问现在，不是问半秒前。

### 8.5 用例

- `tests/e2e/client.mjs` 14g2：三组真实倍率（运行中暂停后继续、倒放作为最后一条、
  暂停后重新开跑），断言整批"2 条成功，0 条失败"（0.10.0 起，现在走计数器路径）。
- 14m3：批次第一条是 `set_time_speed`（0→3600），执行期间把引擎时钟直接加 30 分钟，
  断言第二条不发、停止理由写"观测时间"。
- 14m4（0.12.0）：时钟暂停下，批次 `set_time`（换到另一天）→ `set_fov` → `set_fov`，
  断言三条全发、最后视场到位、状态是"完成"，并且 `jumps` 只增加 **1**——即自身的写入
  被计数而不是被吞掉。这一条就是 8.6 的回归：修复前第二个 `set_fov` 会被自己第一条
  命令的迟到信号拦下。
- `tests/reference/consistency.mjs` 保证提示词里的上限与代码常量不漂移。

### 8.6 自身的写入必须在命令返回前登记（0.12.0）

0.11.0 的计数器只在下一次 `requestAnimationFrame` 里增加。而 `applyTime` 是同步写
`observer.utc` 后立刻 `Promise.resolve` 的：面板在同一个微任务里收到"已执行"，随即
重锚上下文；跳时信号却在**下一帧**才到。于是"把时间设到另一天 → 调视场 → 再调一次"
这种完全合法的批次，会被自己第一条命令的迟到信号当成外部跳时，第三条不再发送。

修正不是"忽略自家的 set_time"（那样会连带吞掉别人经同一桥接写入的跳时），而是把
登记提前到写入处：`applyTime` 在写完、读回之后立刻调用一次
`noteClockWrite(before, after)`——位移超过**写入判据**就 `jumps += 1`，同时把帧基线
重锚到刚写入的值，下一帧不会再数第二次。这样：

- 信号落在**发起它的那条命令**的时间窗内，面板按"`set_time` 允许改时间"豁免它；
- 计数器仍然诚实地增加（14m4 断言 +1），别的写入照旧是外部跳时；
- 帧基线的重锚只发生在本桥接自己写的那一次，不存在"全局吞掉"。

**两种判据不完全相同，别把它们说成同一个**：

| 场景 | 判据 | 为什么 |
|---|---|---|
| 桥接自己的显式写入（`set_time`） | 位移绝对值 > `JUMP_FLOOR_SEC`（固定 **2 秒**） | 目标值是我们自己写下去的、读回也是同一时刻，没有"落后一帧"这回事；改 1 秒也是真的改了，就该计一次 |
| 逐帧外部观测（`requestAnimationFrame` 里） | `2 秒 + 50 ms × 倍率` | 引擎按自己的帧积分，读到的值最多落后一帧；3600 倍下一帧约 60 秒模拟时间，容差必须随倍率放大才不会误报 |

前者更严（不随倍率放宽），后者更宽（必须放过一帧滞后）。显式写入用严判据是安全的，
因为发起方本来就知道自己改了多少；逐帧观测用宽判据是被迫的，代价是倍率越高、能看见的
最小外部跳时越大（见 8.3 的检测下限）。两者共用同一个计数器 `jumps`，所以面板只需比
计数，不必关心是哪一种路径加的。

## 9. 测试

`tests/e2e/timeflow.mjs`（31 项，不需要模型）实测引擎时钟：

- 能力、`bridgeVersion` 与 `features.commandPrecheck` 真的到了 0.7.0
- `1000×` 跑 2 秒，模拟时间前进约 2000 秒（实测 2012）
- `factor 0` 之后 1.2 秒内漂移 0 秒
- 负倍率时间倒退
- `simHours` 折算 `realSeconds` 正确，自动停表真的停，且停在目标附近（实测 182 模拟秒 / 目标 180）
- 换倍率会取消旧停表；`set_time` 会清停表并报 `autoStopCleared`
- 86401、1e-6、`factor 0 + simHours`、`simHours 200000`、折算超 72 小时全部被拒
- 未知字段、字符串 factor 被拒
- §9 组一遍需求场景的命令链：跳时刻 → 木星居中 → `1000× + simHours 24`，断言返回的
  `realSeconds≈86.4`、`stopAtUtc` 等于起点 + 1 天、当前倍率为 1000，然后立即 `stop()`。
  **这一项验证的是计划值和停表机制，不是真跑满 86 秒**；短时自动停表另有独立用例
  （目标 180 模拟秒，实测约 182）。停止靠每 200 ms 一次的检查，所以"停在目标附近"而不是
  "停在目标毫秒上"

`tests/reference/consistency.mjs` 保证提示词里写的上限和代码里的常量不漂移。
